## (d) Adaptations

Deliberate differences from the Node code, each with its reason. Filled during the phase; plan 02-14 reviews it.

1. **FakeRenderer actions.** The Kotlin `FakeRenderer` adds `SetVolume` (stores `DesiredVolume` into `state.volume`), `SetMute` (stores `DesiredMute`, "1" or "true") and `GetMute` (answers `CurrentMute` 1 or 0). The Node fake only answers `GetVolume`/`SetVolume` with a fixed reply. Every other action still answers an empty `u:<Action>Response`. It also XML-escapes the URIs it echoes back in `GetPositionInfo` and `GetMediaInfo`, which the Node fake pastes raw.
2. **D-04 exception: receiver names.** Receivers are named `🔊 {name} (app)` instead of the Node `🔊 {name}` (CAST-07) while the Docker server runs, so the two do not collide in the cast menu. `DOCKER_COEXISTENCE_SUFFIX` is removed at parity.
3. **CAST-08 fixtures.** The lounge fixtures are recorded from the yt-cast-receiver 2.1.0 library harness (`tools/lounge-capture`, dependencies from the Node project's lockfile at 5bd3025), the receiver inside the Node server, instead of the Docker server's logs, which print parsed objects rather than raw frames.
4. **SOAP transport.** `SoapClient` posts a `ByteArray` body through OkHttp (byte-exact `Content-Length`), where Node sets the header by hand from `Buffer.length`. A per-call timeout comes from `Call.timeout()`; cancelling the coroutine cancels the call.
5. **Cleartext guard (SVC-05).** Node has no equivalent. `PrivateLanGuard` refuses plain HTTP to names and to non-private IPs, and `lanHttpClient()` disables redirects, because the manifest allows cleartext app-wide.
6. **DIDL text.** `buildDidl` strips code points outside the XML 1.0 Char production before escaping (RESEARCH Pitfall 10); `upnp.js` only escapes.
7. **Paused seek stays paused.** `Player.seek` on a paused player leaves it paused; yt-cast-receiver resumes it.
8. **Restart-seek while paused.** A restart-seek on a paused player loads the stream without Play and sends Play at resume; Node's `#load` always sends Play.
9. **Pause waits for a starting speaker.** Pause waits, bounded, for a speaker that is still starting; Node sends it at once.
10. **Speaker metadata evidence.** `FakeRenderer` answers `TrackMetaData` and the renderer logs the speaker's metadata as lengths. Kotlin-only evidence, no Node counterpart.
11. **Range on live video pipes.** Live video pipe tokens (adts, mp3) answer ranged GETs from the bytes of the first run: 206 with the true total, a bounded cache (32 MiB per token, 64 MiB total) and a bounded cold fill (8 s). Node's `#pipe` ignores Range and answers 200 from byte 0, which made the Lamp hang up after an early Pause. The switch `PIPE_RANGE_ANSWERING_DEFAULT` ended true (Kitchen Amp retest, forced adts, 2026-10-21). The start clock also restarts at a Play that follows a Pause when the speaker was never seen PLAYING; Node measures from the load only.
12. **Next availability counts the autoplay video.** `Player.getNavInfo().hasNext` is true when the only next item is the autoplay video; yt-cast-receiver counts queue items only. Reason: with the autoplay mix on, the phone's Next button must work on the last queue item (CAST-05).
13. **A stop seen mid-track is mirrored, not advanced.** When the speaker reports STOPPED after PLAYING, the renderer treats it as a track end only when the length is unknown, no position was polled, the position never left the start, or the last position is within `TRACK_END_TOLERANCE_S` (10 s) of the end. Otherwise the stop is mirrored to the phone as STOPPED and the queue does not move. Node advances on every stop. Reason: a Stop pressed in the Sonos app must not skip the queue on.
14. **`config.json` replaces environment variables (SVC-07, D-04).** The tolerant parser keeps the defaults for anything missing or wrong and reports unknown keys in one warning. `outputFormat` defaults to `auto`, as the Node `OUTPUT_FORMAT` does, and an invalid value falls back to the default with a warning instead of failing the start as Node does. The naming keys (`nameSuffix`, `nameTemplate`) are not read, so the `(app)` suffix of adaptation 2 cannot be changed from the file.
15. **Direct proxy policy.** The relay of a `direct` token (`OkHttpUpstreamFetcher`) only talks to https googlevideo hosts, follows one redirect hop and re-checks the target against the policy, and forwards only a plain `bytes=` Range header of at most 64 characters. Node's `#proxy` copies the speaker's Range header unchecked and talks to whatever URL the resolver returned. Reason: the media server is reachable by any device on the LAN, and the cleartext guard of adaptation 5 must hold.
16. **The speaker is cleared when a cast ends, if the author asks for it (CAST-06, GUI-08).** The renderer sends an empty transport URI when the sender disconnects and when the service stops, but only if `GetMediaInfo` shows the URI is ours, and only when the "clear the speaker when a cast ends" setting is on (Phase 7; off by default). With it off a cast end leaves the speaker loaded, and a bridge stop sends Stop only to the speakers playing our stream. A speaker card's Clear button clears unconditionally. Node has no equivalent. Reason: a speaker should not keep showing, or replaying, a stream whose server is gone, but the author may prefer to keep the track loaded.
17. **A recently-asked guard stands in for `markWatched`.** The InnerTube handler drops an autoplay candidate it was asked about in its last 8 calls when the queue is at its last item, which ends the A to B to A Mix ping-pong. `markWatched` (the `/player` stats ping) is not ported and stays deferred.
18. **InnerTube fixtures are hand-trimmed.** The six `/next` fixtures are cut by hand from the response shapes recorded in RESEARCH, not captured from a live session. The real-device check is recorded in 03-DEVICE-RESULTS.md.
19. **The `CACHE_MB` cache replaced the interim cleanup of built files.** Phase 3 kept the newest six finished files and wiped the build directory at start and stop; Phase 4 (PLAY-10) replaced that with the size-capped LRU cache of adaptations 30 to 33 (`media/FileCache.kt`).
20. **Restart offsets and native Seek on offset files.** A restart offset is clamped to one second before the end when the length is known (Node has no clamp). A native Seek on a file built at an offset is relative to that file, and a target before the file's start reloads at the target; Node sends the absolute target.
21. **A track end waits for a playlist refresh in flight.** The renderer waits, bounded by `queueSettleTimeoutMs`, for a refresh before it calls next, and ends STOPPED when nothing advanced. Reason: otherwise a track ending during a refresh stops the queue.
22. **The yt-dlp info JSON goes through a private file, and a failed download is retried with a fresh extraction.** `YtDlpSourceDownloader` writes the earlier lookup's info JSON to a new `rw-------` file after removing anything planted at the path, and passes it with `--load-info-json` and no URL. `FileBuilder` retries a failed download after invalidating the cached resolve, so each attempt extracts afresh (the Node `download retries` rule).
23. **Position after a native Seek is held at the target until the speaker has visibly taken the Seek.** After an accepted Seek the renderer reports the seek target to the sender, not the speaker's RelTime, until the speaker has been seen leaving TRANSITIONING (PLAYING or PAUSED_PLAYBACK after TRANSITIONING), or reports a position near the target (within 3 s of the target plus the time since the Seek, for a fast speaker that never shows TRANSITIONING), or stops, or 15 s have passed (then its own position is used again). When it settles the renderer sends one corrected position if the sender's seekbar has drifted more than 3 s. Node reports the speaker's RelTime immediately. Reason: Sonos reports 0-1 s while TRANSITIONING after a Seek (device session C, 2026-10-21), and the Lamp keeps reporting PLAYING with its OLD RelTime for about 0.7 s after it accepted the Seek before it goes TRANSITIONING (device log 2026-10-21 21:43: the phone was told 1.0 at +250 ms), so a bare PLAYING right after a Seek is not believed. The track-end rule still reads the raw polled position. `SeekPositionTest` has no Node counterpart.
24. **A Seek before the first PLAYING restarts the start-timeout clock; a fallback does not clear a learned format that has played.** The start watchdog (no PLAYING within `startTimeoutMs`) counts from the last command that can delay the first PLAYING, so a native Seek restarts it, and while the Seek is still pending (at most `SEEK_SETTLE_DEADLINE_MS`) the verdict is held back. A hard cap of 4 start timeouts from the load (`START_HARD_CAP_FACTOR`) still ends the wait for a dead speaker that keeps taking Seeks. A start failure clears the remembered format only when it has not played on this speaker in this session. A start-failure reload goes back to the position that was wanted (the load position or the last accepted Seek), and a post-Play Seek the speaker refuses while starting is sent again once it plays (Node sends it once and ignores the answer). Node measures the start from the load only and forgets the format at any start failure. Reason: Lamp seek near the end took 13 s (device session C, 2026-10-21 22:01); the app gave up on a working format and restarted the song. `SeekBeforeFirstPlayTest` has no Node counterpart.
25. **The phone's seekbar is corrected when the speaker's position drifts from it.** The renderer remembers the position and time of the last state it told the sender (`Player.senderPosition`, which counts on while that state was PLAYING) and compares it with each polled RelTime. When they differ by more than 3 s on two consecutive polls, with no Seek hold pending, the player PLAYING and the speaker playing our stream, it sends one corrected position (`Player.notifyPositionCorrection`), at most one correction per 10 s (`DRIFT_MIN_GAP_MS`). Nothing is sent while they agree, so an uneventful track costs no extra messages. Node reports a position only on a state change. Reason: a seek or scrub in the Sonos app, a stale read at a load or pause and a stream restart left the phone's bar wrong until the next event (device session C, 2026-10-21). The track-end rule still reads the raw polled position. `PositionDriftTest` has no Node counterpart.
26. **A connected sender that is no longer in the loungeStatus remote list is dropped.** On a loungeStatus of the active session whose `devices` list parsed, every connected sender whose id is not among the REMOTE_CONTROL ids of the list is removed as an implicit disconnect (`senderNotListed`, then the usual `senderDisconnected`), and the autoplay support is worked out again from the senders that remain. A status with a missing or malformed `devices` list, and the status of an inactive session, drop nobody. Node does not do this: yt-cast-receiver 2.1.0 (`lib/app/YouTubeApp.js`, `loungeStatus` case) changes its connected senders only from the `connectionEventDetails` of a status (and replaces them wholesale when the app is STARTING), never by comparing them with the status list. Reason: force-stopping YouTube Music sends no disconnect, so it stayed connected and kept autoplay UNSUPPORTED for the YouTube app, and the end of the queue logged `noAutoplayVideo: autoplay is not enabled` (device session C, 2026-10-22). `YouTubeAppTest` (ghost sender tests) has no Node counterpart.
27. **The sender is told buffering until the speaker plays after a seek.** After a native Seek the speaker accepted, and after a Play that followed a Seek made while paused, a PLAYING player is reported to the sender as state 3 (loading) at the seek target (`PlayerState.buffering` and `senderCode`, used by `Message.onStateChange` and `nowPlaying`), not as playing. The renderer holds it on the pending-Seek hold of adaptation 23: it ends when the poll sees the speaker leave TRANSITIONING (for the Play after a paused Seek, when it sees PLAYING), or after `SEEK_SETTLE_DEADLINE_MS` (15 s), and then the sender is told playing at the speaker's position once. The player's own status stays PLAYING, so a Pause from the sender still acts during the hold. Node (`lib/Player.js` `seek`) emits LOADING and then PLAYING as soon as the seek call returns, and `resume` emits PLAYING as soon as the Play call returns. Reason: device session D (Lamp, format `direct`, 2026-10-22 06:00-06:08): the Lamp spent 5.8 and 9.6 s TRANSITIONING after phone-driven seeks and 8.6 s after a Play that followed a paused seek, while the phone was told PLAYING within 0.25 s, so its bar ran ahead and was snapped back by the drift check of adaptation 25. `SeekBufferingTest` and three `PlayerTest` tests have no Node counterpart.
28. **The direct proxy reads ahead a bounded window per token.** From the second ranged GET of a `direct` token whose range is bounded and at most 64 KiB (`READ_AHEAD_SCAN_MAX_BYTES`), the proxy answers from a window of 512 KiB (`READ_AHEAD_WINDOW_BYTES`) fetched from upstream starting at the requested offset, and the following small ranges inside it are answered from memory (206 with the true `Content-Range`, the same bytes upstream returns for that Range). One window per token; at most 2 MiB (`READ_AHEAD_TOTAL_BYTES`) held across tokens, windows being fetched included, the oldest window of another token evicted first; a window is dropped when the renderer releases the stream (new track, stop, clear, removal), when the token is evicted, and on a 403 or 410 before the one re-resolve. An upstream that does not answer 206 with a matching `Content-Range` and the full bytes turns read-ahead off for that token (back to one upstream request per speaker request, noted in the log), and a failing window fetch falls back to the plain path. Streams, open-ended ranges and the first ranged GET are relayed exactly as before, and only the speaker's Range selects the upstream range (T-03-06). Every upstream call's time to first byte and total time (milliseconds, no URL) is written to the `upstream` field of the `http-req` event. Node's `#proxy` (`reference/tube2upnp/src/mediaServer.js`, lines 140-175) opens one upstream request per speaker request and pipes it through; it reads nothing ahead and keeps nothing, so a 6144-byte range costs one upstream round trip there too. Reason: device session D (Lamp, `direct`, 2026-10-22 06:00-06:08): after every seek the Lamp asked for 70 to 110 ranges of 6144 bytes about 68 ms apart, each a separate upstream request, and took 6 to 10 s to play, while mp4, flac and mp3 files built on the phone took 1.1 to 1.4 s. That the upstream round trip is the cause is a hypothesis (the Lamp may instead be scanning a non-moov-first m4a itself); the timing field and the device re-measure decide it. `DirectReadAheadTest` and `ReadAheadReleaseTest` have no Node counterpart.
29. **A speaker that is playing a source that is not ours is released after two polls.** When two consecutive polls read a non-empty speaker TrackURI that is not one of our own `/stream/` URIs (any scheme, including `x-sonosapi-*` and `x-rincon-*`) while the renderer has a track and no load, clear or stop is in progress, the renderer stops polling, forgets its track, tells the sender the player stopped (so the cast count drops) and writes one log line (the scheme only, never the URI). Nothing is sent to the speaker and the queue does not advance. One odd reading, an empty or unreadable URI, and a previous track of ours never count; the poll adds no SOAP call. Reason: device session E (Lamp, 2026-10-22 11:55): the author played Sonos radio from the Sonos app, and the notification and the phone kept showing playback of it. Node does not do this. The new `RendererTest` takeover tests have no Node counterpart.

30. **A file referenced by a live token is pinned until the renderer releases it (D-04).** A file token pins its cache file from registration until `MediaRegistrar.release`, token eviction at `MAX_TOKENS` or `MediaServer.stop`, and a response pins the file while it is served; pruning and `clearCache` skip pinned names, so the cap is soft by the size of the playing and prepared files. Node evicts by age and size only. Reason: with a cap of 0 or a small one, the playing track's file or the prepared next track's file must not be deleted under the speaker. The ported test "cache: a file larger than CACHE_MB is still served; older files are evicted first" calls `release(pathA)` first, as the renderer does when it replaces a track; its title and assertions are unchanged. `MediaServerCacheTest`, `FileCacheTest`.
31. **Finished files survive a stop, and the start scan deletes every file that is not a finished cache file (D-12).** Node removes only `.part`, `.download` and `.info.json` leftovers at start. Kotlin keeps finished non-empty `.m4a`, `.flac` and `.source` files across a stop and a service restart and deletes everything else in the directory at start (half-written, empty, yt-dlp leftovers and foreign files). Reason: Android may kill the service at any time, so a restart should not throw away a cache the user paid the download time for, and the directory belongs to the app. `MediaServerCacheTest`.
32. **A file token registers lazily and a missing file is rebuilt at serve time (D-14, D-03).** `registerVideo` for mp4 and flac registers the path of the file to come (`FileBuilder.pathFor`) without building it, and a GET or HEAD of a token whose file is missing (never built, or deleted by Android or by pruning) builds it again, downloading the source again only if that is gone too, bounded by `prepareTimeoutMs`; a failed rebuild answers 502 with a fixed note and no URL, and the token stays registered. Node builds the file in `prepare` and answers an error when it has vanished. `MediaServerCacheTest`, `MediaServerRemuxTest`.
33. **One cap, 256 MB by default, read on every prune, covering source files too (D-01, D-02).** `cacheMb` in `config.json` (0 to 32768) is the single cap over built and source files; Node's `CACHE_MB` defaults to 512 and counts built files. The cap is a supplier read inside every prune, so a changed value applies at the next one; pruning also runs after source downloads for the pipe rung; a source is deleted together with the last built file of its video; the file just built and its source are never evicted by the prune that follows the build. cast-state shows `cache` (files, bytes, limitBytes). `FileCacheTest`, `MediaServerCacheTest`, `BridgeMediaWiringTest`, `BridgeGaplessTest`.
34. **The prefetch runs in its own coroutine and `doStop` keeps the prepared track.** The poll only launches the prefetch (one at a time); it re-checks `loadSeq`, the current and upcoming ids and the destroyed flag under the queue lock before it installs the prepared item, and it pauses while a playlist refresh is in flight. A failed prepare is backed off per video (30 s doubling to 10 min, the last 50 ids). `doStop` leaves the prepared item alone, where Node's `doStop` drops it: the Kotlin `Player.play` stops a PLAYING player before every track change, so dropping it there would make every track-end load prepare the next track again; `load()` reuses or releases the item. `GaplessTest`.
35. **The gapless hand-off waits, bounded, for a playlist refresh in flight, and the Stop shortcut is limited to the hand-off's own `next()`.** When the speaker plays on into the queued track the renderer waits up to `queueSettleTimeoutMs` for a refresh before it calls `next()`; `doStop` skips the speaker's Stop only while that `next()` runs, and a `next()` that cannot run (queue over, nothing to advance to) stops the speaker. Node skips the Stop whenever a switch is pending, so a phone-side Stop during the wait is lost there; in Kotlin it still stops the speaker and the track is not adopted. `GaplessTest`.
36. **Learned gapless support is persisted with the speaker model and asked again after 7 days (D-08, D-13).** The answer to `SetNextAVTransportURI` is stored in the speaker's `store.json` entry as `{supported, model, at}` next to the learned format. A stored true is trusted at any age; a stored false is trusted for 7 days; a value stored for another model is unknown and removed; a malformed value is unknown. An accepted queue call contradicts a false (it becomes true), a classified refusal makes a true false, and a stop at the end of the track instead of the switch makes it unknown again. Node keeps `#gaplessSupported` in memory, so every restart costs a failing call per speaker. cast-state shows it per speaker as `gapless` (true, false or null). Kotlin-original: `GaplessMemoryTest`, `GaplessLearningTest`, `BridgeGaplessTest`.
37. **An unclear `SetNextAVTransportURI` failure is retried up to 3 times.** A failure that is not a classified refusal (a bare HTTP 500, a network error) is retried from the next polls up to 3 attempts per queued track and never marks the speaker unsupported. Node sends it once and does not retry. `GaplessLearningTest`.
38. **A STOPPED reading at the switch gets a 3-poll grace when the speaker holds the queued stream.** When the track ended and the queued track was accepted, a STOPPED poll reads `GetMediaInfo`; while the speaker holds the queued stream and fewer than 3 polls have passed the renderer waits, and a following PLAYING is adopted with no reload, no Stop and no second Play. Past the grace the gapless memory is forgotten and the queue advances with the prepared track. Node treats the first STOPPED as the track end. Reason: a momentary STOPPED at a track change must only delay the adoption, never replay the start of the next track. `GaplessLearningTest`.
39. **A track that cannot be resolved or prepared is skipped, retried first when the reason is unclear (D-11).** A reason YouTube will not change (removed, private, unavailable, age or members restricted, not yet live; `TrackFailures.isPermanentlyUnavailable`) is skipped at once; any other failure is retried after 2 s and 5 s (`Config.playRetryDelaysMs`, code-only) with a fresh lookup and then skipped; 5 unplayable tracks in a row (`MAX_UNPLAYABLE_IN_A_ROW`) or the end of the queue stop the player. The skip note carries the id and a reason class, never the message. Node stops at the first failed track. `UnplayableTrackTest`.
40. **The ported renderer tests drive the real lounge queue and pin adts.** Kotlin `Player.next` and `Player.play` are final, so `GaplessTest` sets the current video and a `PlaylistRequestHandler` that answers what follows, where the Node tests replace `r.next` and `r.getUpcomingVideo` with assigned functions; the tests pin the output format `adts`, so token paths end `.aac`. The 'no gapless support' test also waits for the `Prepared next track` note before `doPlay(B)` (the resolve is recorded before the prepare finishes); titles and assertions are unchanged. The harness defaults mirror Node's `setup()` with `prefetch = false`. `GaplessTest`.
41. **The adopted track counts as playing at once.** `adopt(item, alreadyPlaying)` sets `playSent`, `sawPlaying` and the played format, so the speaker's own position is used immediately and the start watchdog is off for a track the speaker already plays; the switch note names the field that showed the switch (`TrackURI` or `GetMediaInfo.CurrentURI`) and never the URI. `GaplessTest`, `BridgeGaplessTest`.
42. **A start that cannot succeed ends the cast visibly.** Node (and yt-cast-receiver) only set the player to STOPPED and leave the senders connected. Here, when the speaker never starts and no format is left (a forced format or the end of the chain), or the fallback reload cannot prepare or load any format, `Renderer` calls `Player.reportPlaybackFailure`: the senders are told STOPPED (state 4), then `YouTubeApp` sends `loungeScreenDisconnected` on the active session, drops its senders (reported to `onSenderDisconnect` as explicit) and resets the player, which clears the speaker. The D-11 retry and skip of unpreparable tracks is unchanged; a Stop, a newer play or a removal that overtakes the failure cancels it. Reason: Sonos One 2026-10-28 (04-09 baseline LAN): direct fetched but never started, every download got 403, and the phone kept showing playing with an advancing seekbar. `PlaybackFailureTest`, `PlaybackFailureBridgeTest`, `YouTubeAppTest`, `PlayerTest`.
43. **yt-dlp updates itself 30 s after the service starts and every 24 h, on the configured channel.** Node `scheduleYtdlpUpdates` only starts a timer, so its first update comes after `YTDLP_UPDATE_HOURS` (default 24) unless the Docker entrypoint updates first, and it runs `YTDLP_UPDATE_CMD`. Here `YtDlpUpdater` (started by `CastFeature.start`, on its own coroutine and dispatcher) runs the first update 30 s after start-up, retries a failed attempt after 1 h, and uses the channel `ytdlpChannel` in `config.json` (`stable` by default, `nightly` allowed; read before every attempt). There is no interval setting and no custom command. Each attempt writes one `ytdlp-update` evidence event, and no failure of the update reaches the cast path. Since Phase 5 (plan 05-11) the 24 h schedule runs on the elapsed-time clock (`SystemClock.elapsedRealtime`, so time the CPU slept in deep sleep counts), is re-checked at least every 15 minutes and at every housekeeping alarm (`YtDlpUpdater.runIfDue`; the loop and the alarm share one mutex and one deadline, so one deadline gives one update), and a due update waits up to 10 minutes, in steps of 60 s, while a yt-dlp lookup runs (`CachingResolver.inFlightCount`; one `ytdlp-update` event with status `POSTPONED` when the wait starts), so the swap of the yt-dlp files never lands in the middle of a lookup. Reason: PLAY-02; the 403 class of failures is fixed upstream by yt-dlp releases; an unattended phone sleeps between casts, and a coroutine delay does not count the time the CPU slept (RESEARCH Pitfalls 3 and 4). `YtDlpUpdaterTest`, `CachingResolverTest`, `ConfigFileTest`.
44. **Periodic housekeeping every 5 minutes: alive again in LAN mode, a listener self-probe, a speaker search.** `Bridge.housekeeping` runs on its own timer (`HOUSEKEEPING_INTERVAL_MS`, 300 s, six times inside the advertised max-age of 1800 s) and, once the Phase 5 alarm exists, from an external tick; two runs less than half an interval apart (wall clock) collapse into one, except the adb trigger. A run sends `ssdp:alive` for every receiver again in LAN mode only (phone-only mode sends nothing and logs why), sends the responder one probe M-SEARCH with a random `urn:dev-t2u:probe:<16 hex>` target to prove its own listener still receives (on silence it closes and reopens the listen sockets, never the bridge, and probes once more), and searches for MediaRenderers. Node's peer-dial sends `alive` once, when the peer is ready (`reference/libs/peer-dial/lib/peer-dial.js`, `peer.on("ready")`), and has no probe. Reason: Phase 1 lost 2 of 33 multicast probes (01-SPIKE-RESULTS.md row 5) and the phone sleeps between casts, so a lost datagram or a deaf listener must not leave the speakers out of the cast menu for the night. In Doze the external tick is an AlarmManager alarm (plan 05-11: `setAndAllowWhileIdle`, `HousekeepingAlarm` and `HousekeepingReceiver`, 5 minutes ahead, a 60 s wake lock, work bounded to 45 s, cancelled on Stop; `cmd housekeeping` runs a pass at once). Known limit: the 5-minute cadence holds while the phone is awake (screen on, or casting with the wake lock); in Doze the Android documentation says `setAndAllowWhileIdle` alarms fire no more than once per nine minutes per app, so idle runs are at most 9 minutes (540 s) apart and a failed-setup retry comes at most 5 + 9 = 14 minutes after the failure (a revival's first attempt at most 9 minutes after the terminate). Sources: developer.android.com/training/monitoring-device-state/doze-standby and AOSP `AlarmManagerService` (the allowlisted app's alarms get `FLAG_ALLOW_WHILE_IDLE_UNRESTRICTED`, leaving an inexact window of 75 % of the delay). Samsung One UI may stretch alarms further; the `housekeeping-alarm` event's `lateMs` shows the real cadence, measured in plans 05-12 and 05-13. Kotlin-only: `BridgeHousekeepingTest`, `SsdpResponderTest`. Phase 5 gap closure (plan 05-18): housekeeping does not probe, reopen or rebuild anything while the system reports no Wi-Fi, also when `networkLost` has not been called yet (the Wi-Fi rebind off switch that made this the normal case was removed in Phase 7, GUI-10; the no-Wi-Fi guard stays); after two failed probes the responder (and, after a search through a client without a search socket, the SSDP client) is rebuilt on the bridge's own address with the devices the receivers advertised, never when the phone's address differs from the bridge's, and every repair is logged as `ssdp-repair`. Reason: carry-over (c) failed on the phone with the switch off (05-DEVICE-RESULTS.md Session E step 5) and the review found a deaf responder that nothing rebuilt (WR-03). Tests: `BridgeRepairTest`.
45. **A failed speaker setup is retried by a 5-minute timer forever, a receiver that stopped itself is replaced, and the first prune after a long sleep waits for a search (D-05, DISC-05).** Node (`src/index.js` lines 57-81) remembers a device whose setup threw for `RETRY_FAILED_MS` and tries it again only when a later SSDP alive arrives after that time. Here `RendererRegistry.retryDue` sets every such device up again once its 5 minutes are over, without a new alive, then every 5 minutes after each failed attempt, with no back-off and no limit; the schedule checks every 10 s and `Bridge.housekeeping` runs the same check, and every attempt writes a `retry` event (reason, attempt, outcome). A device refused as not a usable renderer is still never retried, and the memory of skipped devices holds at most 256 entries. Node (`src/renderer.js` lines 174-177) only records `lastError` when the cast receiver terminates itself; here the renderer builds a new receiver from the same options (same DIAL port, name and per-speaker store) 10 s later, then every 5 minutes until a start works (`retry` event with reason `terminated`). The first prune after a gap longer than twice the discovery interval since the last search is deferred behind a search (`prune-deferred`), so waking the phone never removes every speaker at once. A retry pass that is cancelled (the housekeeping alarm bounds its pass to 45 s) releases every reservation, destroys a half-built renderer and frees its port, and leaves the skip entries alone; a due time more than one retry period ahead of the wall clock counts as due, so a backwards clock jump does not delay retries. Reason: an unattended phone (D-05, ROADMAP criterion 4 of Phase 5; DISC-05 on an unattended phone, Phase 5 gap closure, plan 05-14). Tests: `RendererRegistryTest`, `ReceiverRevivalTest` (Kotlin-only).
46. **A network change moves the bridge in place and the loaded track is re-set at the speaker's position from the new address (SVC-04, D-07).** Node binds its servers once to a fixed address and has no rebind; a changed address means a restart. Here `Bridge.rebindNetwork` moves the media server (same port, tokens, pins and caches kept), the SSDP responder and client and every receiver's DIAL server to the new address without rebuilding renderers, players or lounge sessions, and every renderer is told (`onNetworkChanged`). Between `Bridge.networkLost` and the next rebind no speaker poll runs (`onNetworkLost`), so a stream broken by the move is not mirrored to the phone. After the move a renderer builds stream URLs with the new address and still counts a URL with one of its last 4 earlier addresses (`ownHosts`) as its own, so a speaker that still holds an old-address URL is not released as another source (adaptation 29). A renderer whose player is playing, paused or loading then re-sets the loaded track in its own scope: it waits (at most 20 s) for a load in flight, reads the position once (`GetPositionInfo` plus the stream offset; the last polled position when that fails, never an extrapolation over the outage), drops the prepared next track (it is prepared again with the new address) and sends Stop, `SetAVTransportURI` and, for a playing track, Play (pipe formats restart at the offset, seekable formats Play then Seek). A paused track stays paused: file formats are built at the offset, a paused `direct` stream owes its Seek until the phone resumes and the speaker plays. A stopped or idle renderer sends nothing, and the re-set never sends SetVolume or SetMute. A move back onto the same address re-sets too (the media engine restart cut the speaker's connection); a short gap is accepted. Reason: ROADMAP Phase 5 criteria 2 and 3 on a phone whose Wi-Fi drops or address changes. Tests: `BridgeRebindTest`, `MediaServerRebindTest`, `NetworkChangeTest` (Kotlin-only).
47. **The lounge RPC reconnect rides out network errors for up to 120 s on the same token before refreshing it.** yt-cast-receiver's `RPCConnection` terminates after 3 failed connects and `Session` then refreshes the lounge token, which ends the session when that fails too. Here, when the reconnect fails with a network error (an IOException that is not the lounge answering with an HTTP status), `Session` keeps retrying the same token with waits of 2, 4, 8, 16 and 30 s (30 s repeating), logging each as a `lounge-session` event `rpc-wait` (attempt, waitMs), until 120 s (`rpcOutageBudgetMs`) have passed since the first failure; then the existing refresh path runs. An HTTP status failure never waits. Reason: Phase 5 Wave 0 measurement (`05-DEVICE-RESULTS.md`, `Q1 verdict: sessions-end`): the phone's YouTube Music app ended its own cast in one of five Wi-Fi outages, so the conservative reading builds the tolerance. Tests: `SessionTest` (Kotlin-only).
